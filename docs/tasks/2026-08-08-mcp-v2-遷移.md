# 遷移到 mcp SDK v2 API

狀態:進行中
強度:L2
日期:2026-08-08

## 目標

讓 mcp-fda 的 MCP 整合真的支援 `mcp` SDK 2.x,不是繼續釘死在 1.x
(見 `K-4`:目前釘 `mcp>=1.13.1,<2` 只是暫時擋血,不是長期解法)。
`mcp` 官方 1.x 線已進入維護模式(只收安全修補),長期停在 1.x 不是可持續的位置。

## 範圍

**包含**:
- `pyproject.toml` 的版本區間從 `<2` 改成正式支援 `2.x`(含上限,不留浮動風險)
- 三個對外入口檔案(`src/server.py`、`src/http_server.py`、
  `src/protocol/base_server.py`)的 handler 註冊方式,從 v1 的 decorator API
  改成 v2 的建構子 callback API
- 順便修 `K-1`(`requires-python` 下限過期)——這次的版本區間變動剛好是
  觸發它的原因,一起處理比留著不一致更合理
- 補上這三個入口檔案目前完全零覆蓋的測試(修 `K-4` 「已修(無守備)」
  欠的守備)

**不包含**:
- `src/protocol/sse_server.py` 死代碼清理——性質不同,不混進這次(已在
  `docs/tasks/2026-08-07-mcp-spec-升級.md` 的規模量測階段記下,留給
  之後單獨處理)
- v2 新能力(OAuth 擴充、logging capability 等)——現有程式碼沒用到,
  不主動加
- SSE 傳輸要不要換成 v2 主推的 Streamable HTTP——這是架構層的選擇題,
  不是相容性修復,這次不動
- `tools/registry.py`、`tools/base.py`、`tools/handlers/graphrag_handler.py`
  ——已實測確認 v2 的 `_dump_result` 接受裸 dict 回傳,這幾個檔案的邏輯
  不需要變更

## 驗收

1. 乾淨 venv `pip install -e ".[dev]"` 裝出來的是 `mcp` 2.x
2. `import server, http_server, protocol.base_server` 全部成功,且
   `Server` 建構時四個 handler(`list_tools`/`call_tool`/`list_prompts`/
   `list_resources`)都用 v2 的建構子傳入方式,不再有 `@server.xxx()`
3. 新增的測試能證明四個 handler 真的能被呼叫、回傳形狀正確(不是只測
   「能 import」)
4. `pytest` 全數通過,且比修改前多至少 3 個測試(對應三個入口檔案)
5. `docs/KNOWN-ISSUES.md` 的 `K-1` 狀態更新、`K-4` 的「無守備」註記拿掉
   或更新

## 假設(若不對請說)

1. v2 的 `_dump_result`(`mcp/server/runner.py`)接受裸 dict 回傳,不需要
   建構真正的 `CallToolResult`/`ListToolsResult` 等 pydantic 物件——已讀
   官方原始碼確認,不是推測
2. `CallToolRequestParams` 的 `name`/`arguments` 欄位跟現有程式碼手動
   duck-type 出來的 `CallToolRequest` 形狀相容,`handle_call_tool`/
   `handle_tool_call` 內部邏輯不需要跟著改

- [ ] `pytest` 全數通過
- [ ] 手動啟動 `mcp-fda`(stdio 模式)一次,確認不是「import 得過但一啟動
      就炸」

## 回退方式

單一分支 `feat/mcp-v2-migration`,`git revert` 這個分支合併進 `main` 的
merge commit即可完整還原到 `mcp<2` 的狀態(phase A 的 stopgap PR 若已經
合併,revert 之後會回到那個狀態,不是回到完全未修的狀態)。
